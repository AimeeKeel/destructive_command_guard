# Amp Integration

> Last updated: 2026-10-21 (first-party support, issue #577)

[Amp](https://ampcode.com) does not ask before running tools. Its documented
way to control tool use is a plugin: Amp runs plugins with Bun and calls each
plugin's `tool.call` handler before a tool runs, and a handler that returns
`reject-and-continue` blocks the call
([plugins](https://ampcode.com/docs/customize/plugins),
[plugin API](https://ampcode.com/docs/plugin-api)). dcg generates such a
plugin, which sends every shell command to dcg before Amp runs it.

```bash
dcg install --amp              # ${XDG_CONFIG_HOME:-~/.config}/amp/plugins/dcg-guard.js
dcg install --amp --project    # <repo>/.amp/plugins/dcg-guard.js
dcg install --amp --force      # rewrite the plugin even when it is current
dcg uninstall --amp            # remove the user-level plugin dcg wrote
```

Reload plugins afterwards (Ctrl+O, then `plugins: reload`) or start Amp
again. `amp plugins list` shows whether the plugin loaded.

The user-level file is a system plugin, so it applies to every project on
the machine. A project copy applies only inside that repository and, under
Amp's precedence rules, takes the place of a system plugin with the same
name. Amp's older `amp.permissions` rules with a `delegate` helper are no
longer in Amp's settings schema, so dcg does not use them.

## What the plugin does

For each tool call, the plugin finds the shell command with Amp's
`shellCommandFromToolCall` helper (which recognizes the `Bash` and
`shell_command` tools), and also reads the raw `cmd` and `command` inputs, so
neither can hide the other. It then runs

```
<dcg> --agent amp
```

with `{"tool_name":"Bash","tool_input":{"command":"…"},"dcg_explicit_verdict":true}`
on stdin, in the command's working directory when Amp supplies one. (On
Windows the plugin sends the tool name `shell` instead, so dcg evaluates the
command under every shell dialect: Amp does not document which shell runs it
there.) `--agent amp` selects the `[agents.amp]` profile in dcg's config.

| dcg answer | what the plugin returns to Amp |
|---|---|
| `{"dcg_verdict":"allow"}` (allow, warn) | `allow` |
| `deny` | `reject-and-continue` with dcg's reason, which the agent sees |
| `ask` (a review rule, or a command dcg could not verify in time) | Amp's confirmation dialog: **Run** allows it; declining, dismissing, or a session with no UI (`amp -x`) rejects it |

Non-shell tools pass through untouched. A tool Amp's helper does not know
but whose input carries a `cmd` or `command` string is checked anyway, and a
log line says so.

### Failing closed

Amp does not document what happens when a `tool.call` handler throws, so the
plugin never throws. Every failure becomes a rejection:

- a shell call with no command string (`cmd`/`command` missing, empty, or not
  a string);
- dcg cannot be started, is killed or times out (10 seconds), exits non-zero
  without a verdict, prints nothing, or prints something that is not a
  verdict;
- the plugin itself fails.

`DCG_BRIDGE_CRASH_DECISION=allow` in Amp's environment lets commands through
when dcg gives no verdict (the same opt-out as dcg's OpenCode plugin); a
deny or ask from dcg still applies. `DCG_BYPASS=1` skips the check entirely,
as it does in hook mode. If the plugin cannot register its handler (an Amp
without `amp.on`), it throws while loading, so Amp reports it as failed
instead of loading it without a guard.

What the plugin cannot control is Amp not loading it at all (a deleted or
edited file, or plugins disabled for the workspace). `dcg doctor` checks the
file.

## Checking it

When Amp appears to be installed (`~/.config/amp` exists, or `amp` is on
`PATH`), `dcg doctor` reports the `amp_plugin` check: current, missing, or
dcg-owned but different from what this dcg writes (edited, or generated by a
different dcg version; the embedded dcg path alone does not count).
`dcg doctor --fix` writes or refreshes it, pointing it at the dcg that runs
the fix.
A file named `dcg-guard.js` that dcg did not write is never overwritten or
removed; move it aside first.

To see a block without Amp, run the same request the plugin sends:

```bash
printf '%s' '{"tool_name":"Bash","tool_input":{"command":"git reset --hard"},"dcg_explicit_verdict":true}' \
  | dcg --agent amp
```

This prints a `hookSpecificOutput` deny. With `git status` it prints
`{"dcg_verdict":"allow"}`.
